Kiraya — UI/UX Implementation Handoff

Kiraya Product Design Specification

For Claude Code implementation on the existing Supabase backend contract. Modernist design system, approved.

A. Design System Recap

Approved and unchanged: Modernist — flat, architectural, near-monochrome ground (#f3f2f2 / #201e1d) with a single accent #ec3013, Archivo throughout, Lucide icons, zero corner radius, 2px structural rules, flush-left labels. All new screens extend the Org Dashboard / Platform Admin Dashboard shells — same sidebar, topbar, KPI-strip, table, and tag patterns. No new colors, fonts, or shape language.

UI behavior by permission level
  • No access — nav item and route hidden entirely (not disabled), unless landing there directly renders a "You don't have access to this area" page explaining who to ask.
  • View-only — action buttons render visibly but disabled, with a tooltip explaining why ("Requires Accountant or Admin role"); a persistent page banner states the view-only condition once (see Org Dashboard's banner).
  • Edit — full CRUD on that entity; financial actions (payments, void, reversal) still gated separately.
  • Admin/Financial — unlocks destructive + monetary actions, always behind explicit confirmation (Section F).

Frontend gating is UX only — Supabase RLS is the actual security boundary; the UI must degrade gracefully (disabled, not silently broken) if a call is rejected server-side.

E. Screen Specifications — Built Screens
Organization Dashboard BUILT

Purpose: single-glance answer to "how is this organization doing today." Access: all org roles (Viewer sees read-only banner). Layout: sidebar + topbar shell; 6-cell KPI strip (Properties, Units, Occupancy, Tenants, Outstanding, Collected); 2-column body — Collection Performance chart + Recent Payments table (left, 2fr), Pending Actions + Lease Expiries (right, 1fr); full-width Billing Status strip. Primary actions: Record Payment (topbar, permission-gated). Empty state: KPI strip still renders with zeros; Recent Payments/Pending Actions show "Nothing here yet" row. Mobile: KPI strip becomes 2-column scropóll grid; two-column body stacks to single column, chart before table.

Platform Admin Dashboard BUILT

Purpose: cross-organization health at a glance. Access: Platform Admin only. Layout: dark sidebar (visually distinct mode); KPI strip (Organizations, Active, Properties, Units, Outstanding, Collected); Operational Alerts strip; Organization Health table (sortable, links into org context); Platform Collections chart. Primary actions: row click → Organization Detail. Empty: n/a (platform always has ≥1 org in practice — if zero, show "No organizations yet · Add organization" CTA).

Tenant Detail BUILT

Purpose: the tenant's single source of truth — who/where/lease/owed/paid/credit/documents in one workspace. Layout: header band (name, unit/property, status tag, contact) + 5 summary tiles (Current Rent, Outstanding, Available Credit, Deposit Held, Lease Ends) + tabs: Overview, Lease, Bills, Payments, Ledger, Documents, Exit. Permissions: Viewer sees all tabs read-only; Accountant sees payment/credit actions; Exit tab only actionable by Accountant/Admin. Empty: new tenant with no lease shows "No active lease — Create Lease" in Lease tab; Bills/Payments tabs show "No bills yet" until first billing run.

Property Detail BUILT

Purpose: operational workspace for one property. Layout: header (name, address, owner chip) + summary tiles (Units, Occupancy, Tenants, Outstanding) + tabs: Overview, Units, Owners, Financials, Documents. Units tab table links to Unit Detail → Tenant Detail. Permissions: edit gated to Operational role and above.

Bill Detail BUILT

Purpose: financially explicit single-bill view. Layout: header (bill #, tenant, property/unit, period, status tag) + charges table + adjustments + total rule + payment summary strip (Paid / Credit Applied / Outstanding) + Payments-against-this-bill table. Actions: Finalize (Draft only), Void (Finalized/unpaid only, strong confirmation), Record Payment shortcut. All gated by Accountant/Admin; Viewer sees numbers only, no action buttons rendered (not just disabled — bill actions carry real financial weight, so they're hidden with a one-line "Financial actions require Accountant access" note instead of a disabled button row).

F. Financial Confirmation Pattern

Every financially destructive or irreversible action uses the same dialog structure (Modernist .dialog, no rounded corners, 2px border):

  • Title states the action in plain verbs: "Void Bill #INV-2201", "Reverse Payment of ₹18,500", "Refund Security Deposit".
  • Affected line: tenant/property/unit named explicitly.
  • Amount shown large, tabular-nums, with before/after where relevant (e.g. "Outstanding will change from ₹0 to ₹18,500").
  • Reversibility stated in one line: "This cannot be undone" or "This creates a reversal — original record is preserved for audit."
  • Confirm button is accent-filled and restates the verb ("Void Bill", never generic "Confirm"); Cancel is .btn-secondary, listed first (left) so Cancel is the default visual weight.
  • For amounts ≥ a configurable threshold (OPEN PRODUCT DECISION — no such threshold exists in the backend today), consider requiring the user to type the amount to confirm — flagged as optional hardening, not required for v1.

Applies to: Finalize Bill, Void Bill, Record Payment, Allocate Payment, Apply Credit, Reverse Payment, Reverse Allocation, Refund Deposit, Complete Tenant Exit, remove Member, delete Property/Unit/Owner records with dependent data.

G. Key Screen Specs — Remaining Areas
Properties / Tenants / Owners / Leases — List screens

Layout: topbar with page title + primary "+ Add" action (permission-gated) + filter row (property, status, search) + Modernist table. Columns — Properties: Name, Address, Owner, Units, Occupancy, Outstanding (right-aligned). Tenants: Name, Unit/Property, Lease status, Outstanding, Last Payment. Leases: Tenant, Unit, Start, End (with expiry tag if <30 days), Rent, Status. Row action: click → detail; overflow menu for Edit/Archive. Pagination: 25/page, standard Modernist pagination component. Empty: icon + "No properties yet" + one-line explanation + primary CTA. Loading: skeleton rows (5), header stays static.

Create/Edit forms (Property, Unit, Owner, Tenant, Lease)

Right-side drawer (not full page, not modal) for single-entity CRUD — keeps list context visible. Sectioned fields (Identity → Location/Ownership → Financial defaults). Required fields marked with a small dot, not asterisk-in-red (accent reserved for status/errors). Inline validation on blur; submit disabled until valid; success closes drawer and highlights the new/updated row briefly (background flash, not a toast alone). Lease creation is a 2-step drawer: Party & Unit → Terms & Billing Config, because rent/billing setup materially changes downstream billing runs.

Billing Dashboard & Billing Runs

Billing Dashboard: KPI tiles (Bills this cycle by status, per Section A tag table) + "Run Billing" primary action + Runs table (Period, Scope, Tenants, Bills Generated, Status, Started by). Run detail: Review step shows scope (properties/units count, tenant count) before running; Processing shows a progress state (inline, not full-page spinner); Completed shows a summary (Generated / Skipped / Failed) with drill-down into any failures, each with a specific reason (never a raw DB error) — e.g. "Skipped: Unit B-104 has no active lease."

Payments — List / Detail / Record / Reversal

List: Tenant, Method, Amount, Date, Status (Paid/Reversed), Allocated vs Unapplied indicator. Record Payment (drawer): Tenant search → Amount → Method → Reference → auto-suggested allocation against oldest outstanding bills (editable) → remaining amount becomes Available Credit if any. Detail: amount, method, date, reference, full Allocations table (Bill, Amount Applied), Available Credit line if unapplied remainder exists, Reverse action (Accountant/Admin, full confirmation per Section F — shows each allocation that will be undone).

Available Credit

Always labeled "Available Credit: ₹X" — never a negative balance. Shown on Tenant header tile, Payment detail, and as an "Apply Credit" action inside Bill Detail when a tenant has both an outstanding bill and available credit. Applying credit reuses the confirmation pattern (Section F): states which bill(s) it will offset and the resulting outstanding.

Ledger (org-wide + tenant tab)

Chronological table: Date, Description, Reference, Debit, Credit, Running Balance — Debit/Credit in separate right-aligned columns (never a single signed column) so the sign is never ambiguous. Filters: date range, property, tenant, entry type. Export button (CSV) top-right. Tenant Ledger tab is the same table scoped to one tenant, embedded without its own page chrome.

Security Deposits

Overview: per-tenant Deposit Held, with a Transactions sub-table (Received, Deduction, Refund entries chronologically). Refund is only reachable through the Tenant Exit workflow (Section H) — not as a standalone button — because a refund amount depends on the settlement calculation, avoiding a route to refund a deposit outside that reviewed context.

Utilities & Meters

Utility config/rates: simple table (Utility, Rate, Unit, Effective From). Meter Reading Entry: optimized for repeat data entry — single-column form per meter showing Previous Reading and Previous Date read-only beside the New Reading input, live-computed Consumption, inline range-validation ("this is 40× the prior reading — confirm?") rather than blocking. Consumption history: small line chart + table per meter.

Documents

Contextual document lists embedded in Property/Unit/Tenant/Lease detail (Documents tab) plus one org-wide Documents screen with an Entity-type filter. Upload via drag-drop zone; each row shows filename, type tag, linked entity, uploaded-by, date; preview opens in a side panel for PDFs/images, download for other types. Delete requires Admin and a lightweight confirmation (non-financial, so a single-step confirm suffices).

Imports

Upload → Validation (shows row-level preview before committing) → Processing (inline progress) → Result: Success / Partial Success / Failed, each listing a table of Row, Field, Error, Suggested Correction — plain-language errors only, e.g. "Row 14: Unit code 'B-1O4' not found — did you mean 'B-104'?" Users can download a corrected-rows-only CSV to re-upload.

Reports

Reporting Center landing: category tiles (Financial, Occupancy, Tenant, Owner) → each opens a report view sharing one layout — filter bar (date range, property, tenant/owner/unit, status) + summary tiles + table/chart + Export. 12 reports from the brief (Tenant Outstanding, Occupancy, Meter Consumption, Tenant Milestones, Lease Expiry, Owner Portfolio, Exit Statement, Tenant Dues, Tenant Ledger, Tenant Bill Summary, Collection Performance, Collection by Payment Method) all reuse this shell — no bespoke layouts.

Administration & Platform Organizations

Org Settings: single settings page, sectioned (Identity, Billing defaults, Locale/currency). Members: table (Name, Role, Status, Last Activity) + invite drawer + role change via inline select with confirmation if downgrading own/other admin access. Platform Organizations: same List/Detail/Members pattern as an org's own Members screen, plus a Health tab (the KPI/table combination already on the Platform Dashboard, scoped to one org) and a "View as this organization" action that hands off into the Org shell.

H. Financial Workflows — Detail
Tenant Exit (9-step guided workflow)

Full-page wizard (not a drawer — too consequential), left-side numbered step rail, each step reachable only after the prior is complete:

  • 01 Exit Initiation — select tenant/lease, proposed exit date
  • 02 Tenant/Lease Review — confirms the lease being closed, read-only recap
  • 03 Outstanding Dues — all unpaid bills for this tenant, itemized
  • 04 Deposit Review — deposit held, transaction history
  • 05 Adjustments — any final charges/credits added for this exit
  • 06 Settlement — computed net: Outstanding Dues − Deposit Held ± Adjustments
  • 07 Final Statement — printable/exportable summary tenant receives
  • 08 Refund / Amount Payable — clearly labeled direction (refund to tenant vs. amount tenant still owes), never a signed number alone
  • 09 Completion — confirmation dialog (Section F pattern) → lease closed, unit set to Vacant, deposit transactions posted

Example settlement block: Outstanding dues ₹25,000 · Deposit held ₹50,000 · Deductions ₹10,000 · Refund due ₹15,000. Fields shown must match the backend's actual settlement columns — exact field list is an OPEN PRODUCT DECISION pending schema confirmation for "Adjustments."

Record Payment → Allocation

Entry: Payments list "+ Record Payment" or Tenant Detail → Payments tab. Intent: log money received and apply it. Step 1 select/search tenant. Step 2 enter amount, method, date, reference. Step 3 system proposes allocation oldest-bill-first; user can adjust per-bill amounts. Validation: sum of allocations cannot exceed payment amount; remainder becomes Available Credit automatically. Success: payment + allocations created, affected bills' status updates live. Failure: inline error, amounts preserved. Edge case: payment exceeds all outstanding — full amount becomes credit, no allocation required.

Reverse Payment

Entry: Payment Detail → Reverse. Intent: undo a payment recorded in error. Step 1 confirmation dialog (Section F) listing every allocation that will be undone and the resulting outstanding on each affected bill. Step 2 confirm → original payment marked Reversed (preserved, not deleted), allocations undone, bill statuses revert. Failure: blocked with explanation if downstream state prevents it (e.g. tenant already exited) — OPEN PRODUCT DECISION on exact blocking rules pending backend confirmation.

Finalize / Void Bill

Finalize: Draft → Finalized, locks charges from further edits, becomes payable. Simple confirm (non-monetary-reversal risk, lighter dialog). Void: only available pre-payment; Section F full dialog stating the bill amount and that it's excluded from all totals/reports once voided, with reason field required for audit.

J. Responsive Rules

Desktop (≥1280px): full sidebar + multi-column layouts, primary operational surface. Tablet (768–1279px): sidebar collapses to icon rail (expandable on hover/tap), KPI strips wrap to 3 columns, two-column detail bodies stack. Mobile (<768px): sidebar becomes a bottom-sheet/hamburger drawer; dashboards, tenant summaries, payments, and approvals remain fully usable; wide operational tables (Ledger, Billing Runs, Imports) switch to a stacked card-per-row layout with the same fields, not a horizontal scroll. Financially destructive actions keep the same confirmation dialog full-screen on mobile.

K. Accessibility
  • All status communicated by tag + icon, never color alone (Section A).
  • Every interactive element has a visible :focus-visible accent outline (Modernist default) — never suppressed.
  • Dialogs trap focus, return focus to the trigger on close, and are dismissible via Escape.
  • Tables use real <th>/scope semantics; icon-only buttons carry aria-label.
  • Disabled action buttons carry an explanatory title/tooltip, not just a lowered opacity.
  • Text contrast: body copy never rendered in raw accent red (use --color-accent-700) per design system guidance.
L. Open Product Decisions
Late-fee behavior — automatic vs. manual adjustment. Not defined in backend audit scope.
Notification/reminder cadence for overdue bills and lease expiries — no scheduling model confirmed.
Approval workflow before finalizing a bill or completing a tenant exit (single-actor vs. maker-checker) — not present in current backend.
Threshold for requiring "type to confirm" on large reversals/refunds — no such rule exists today.
Exact Tenant Exit "Adjustments" field set — pending confirmation against the actual settlement schema.
External payment gateway / WhatsApp / tenant self-service portal — explicitly out of scope unless the backend gains support.
Saved/reusable filter presets on report and list screens — no persistence model confirmed yet.
M. Recommended Implementation Order
  1. Application shell (sidebar, topbar, org switcher, permission plumbing) + Org Dashboard, Platform Admin Dashboard — reuse built screens as-is.
  2. Properties → Units → Owners (read paths first, then create/edit drawers).
  3. Tenants → Leases (read paths, then create/edit) — reuse built Tenant Detail.
  4. Billing: Bill list/detail (reuse built Bill Detail) → Billing Runs → Finalize/Void.
  5. Payments: record → allocate → detail → reversal.
  6. Ledger (org + tenant tab), Available Credit surfaces.
  7. Security Deposits + Tenant Exit workflow (depends on 4–6 being live).
  8. Utilities/Meters, Documents, Imports.
  9. Reports (built last — depends on every other data surface existing).
  10. Administration (Members/Roles) + Platform Organizations views.
